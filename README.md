# Maintainer's Will

*A dead man's switch for open source projects.*

> [!WARNING]
> **Not production-ready.** This is an early **v0.1** prototype. Do not rely on
> it to hand over a real project yet: the handover is a dry run that grants no
> rights, the activity heuristics are unproven, and none of it has had a
> security review. Treat it as a proof of concept.
>
> **Generated by Claude.** This codebase was written by Claude (Anthropic's
> Claude Code) from a specification. Review it yourself before running it
> anywhere that matters.

Projects rarely die because a maintainer dies. They die because a maintainer
quietly disappears — burnout, a new job, a kid, illness — and no one has the
keys. For that case there is, today, no tool.

- GitHub's [successor setting](https://nesbitt.io/2026/06/16/how-open-source-projects-change-hands.html)
  only triggers on a **death certificate**, and only covers repos — not registry accounts.
- Registry hand-off processes (CPAN `ADOPTME`, RubyGems ownership calls,
  PyPI [PEP 541](https://peps.python.org/pep-0541/)) are **manual and only kick in after**
  a maintainer has already vanished.
- A `repostatus` badge or "looking for maintainers" in the README is a signal to
  humans that **no tool reads**.

And the other side is just as real: in June 2026 an attacker took over 400
orphaned AUR packages and slipped a malware download into each. `event-stream`
(2018) and `xz` (2024) were hand-offs to strangers with no vetting. **Open
adoption without a gate isn't a feature — it's an attack vector.**

> **Your project needs a will.**

A `WILL.md` in your repo names your successors *in advance*, and a GitHub Action
watches for your inactivity. If you go silent, it moves through **public,
reversible stages** — a private reminder, then a public warning with a deadline,
then a handover — and a single sign of life from you resets everything. Nothing
happens in secret, nothing happens instantly, and **no rights are ever granted
without an explicit human approval.**

## Quickstart

```bash
npx maintainers-will init
```

Three questions (your login, your successors, your inactivity window) and you
get a `WILL.md` plus a weekly workflow. Then:

```bash
npx maintainers-will simulate   # watch the whole flow play out, day by day
npx maintainers-will status     # current stage and time until the next one
```

Commit the files, open a pinned issue titled **"Maintainer's Will"**, and the
action takes it from there.

### What it does — and what it never does

| It does | It never does |
| --- | --- |
| Measures **your** activity (commits, comments, reviews, releases, `/alive`) | Count bot commits or Dependabot PRs as you |
| Records the stage in `.will/state.json` and a shields.io badge | Do anything in secret |
| Posts every stage change to the Will issue with deadlines | Grant repo rights without a human approving it |
| Resets to active on a single sign of life | Let a stranger start the process |

## The stages

| Stage | Trigger | Badge |
| --- | --- | --- |
| **active** | weekly run | `will: active · seen 3d ago` (green) |
| **reminder** | 50% of the window without a signal | green (private nudge) |
| **warning** | full inactivity window | `warning` (orange) |
| **handover** | grace period elapsed | `succession` (red) |
| **handed over** | a successor approved | `handed over` (blue) |
| **fallback** | no approval in time | `seeking adopter` (grey) |

A single maintainer signal returns any active stage to **active**; the log stays.

## Status: v0.1

This is the read-only core. It reads signals, computes the stage, writes state
and the badge, and comments on the Will issue. **The handover is a dry run — it
grants no rights.** Rights escalation behind an environment-gated approval
arrives in v0.2. See [SPEC.md](./SPEC.md) for the full design and threat model.

It is **not production-ready** and has not been security-reviewed — see the
warning at the top of this file. This repo dogfoods itself: see [WILL.md](./WILL.md).
